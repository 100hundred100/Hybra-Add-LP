# 仕様駆動実装ワークフロー

このワークフローの目的は、確定済みの仕様書に基づいて、TDD 原則で実装と検証を完了させることです。

## フェーズ 0: /sign 教訓ガードレール（自動発火）

実装に入る前に、以下を確認する。該当するものは実装中に必ず遵守すること。

| # | チェック | 遵守事項 | 参照ルール |
|---|---------|---------|-----------|
| 1 | DB クエリを書くか？ | 全クエリに `organizationId` フィルタ必須 | `security-by-design.md` |
| 2 | UI テキストを追加するか？ | ハードコード禁止、`t("key")` 経由 + 4言語 JSON 同時更新 | `i18n-first.md` |
| 3 | 環境変数を追加・参照するか？ | `requireEnv` vs `?? default` を使い分け、`.env.example` 同期 | `manus-deployment.md` |
| 4 | 外部ライブラリを使うか？ | ラッパー関数経由、バージョン完全固定 | `third-party-integration.md` |
| 5 | 300行超のファイルに追記するか？ | 分割を検討（ルーター → ドメイン別、コンポーネント → サブ分離） | `file-size-guard.md` |
| 6 | UI / CSS を変更するか？ | `preview_screenshot` で確認→コミット、同一箇所3回修正で中断 | `visual-verification.md` |
| 7 | server/ で `console.log` を使うか？ | 禁止。`createLogger` 経由の構造化ログを使う | `architecture-compliance.md` |
| 8 | 広範囲の変更か？ | `git diff main --stat` で先祖返りチェック | `anti-regression.md` |

## フェーズ 1: 事前調査

1. **仕様書を熟読**: `spec/feature-*.md` の Acceptance Criteria を把握
2. **アーキテクチャを確認**: `docs/architecture.md` で変更レイヤーと依存方向を確認
3. **既存実装を調査**: 対象ファイルを Read / Grep で確認し、影響範囲を把握
4. **実装計画を宣言**: どのファイルに何を変更するかを短く共有
5. **教訓チェック**: フェーズ 0 の該当項目を特定し、実装計画に制約として明記する

## フェーズ 2: テスト駆動開発

### Red
- Acceptance Criteria をテストケースに変換する
- テストが失敗することを確認する

### Green
- 最小限の実装でテストを通す
- 依存方向、ログ規約、例外処理規約、既存パターンを守る

### Refactor
- 可読性、重複、責務分離を改善する

## フェーズ 3: 検証

以下を基本として、存在するコマンドを実行する。

```bash
pnpm test
pnpm check
pnpm build
```

- コマンドが存在しない場合は、等価コマンドで代替する
- テスト、型チェック、ビルドのうち何を実行したかを完了報告に含める

## フェーズ 4: TODO更新と完了報告

### TODO更新
検証がパスしたら、`todo.md` を確認し:
- 実装した機能に対応する `[ ]` 項目を `[x]` に更新
- 該当項目がなければ、適切なセクションに完了項目として追記

### 完了報告
- 変更ファイル一覧と差分サマリー
- テスト結果
- Acceptance Criteria の充足状況
- 実行した検証コマンド
