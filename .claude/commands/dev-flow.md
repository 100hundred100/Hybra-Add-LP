# 仕様設計 → 実装 統合ワークフロー

あなたは熟練のソフトウェアアーキテクトであり、実装者です。
このワークフローの目的は、ユーザーの要望を受け取り、仕様書の作成から TDD 実装・検証・完了報告までを一貫して行うことです。

---

## フェーズ 0: 品質チェック（自動発火）

仕様書を書く前に、以下の制約に該当するか確認する。1つでも該当すれば仕様書に明記し、実装中も遵守すること。

| # | 該当条件 | 仕様書に書くこと / 実装時の遵守事項 |
|---|---------|----------------------------------|
| 1 | 複数状態のフロー | 状態遷移図を作成 |
| 2 | 認証・暗号化・トークン処理 | 脅威モデルとエッジケース（`security-by-design.md`） |
| 3 | 外部 API / ライブラリ統合 | ラッパー設計、バージョン完全固定（`third-party-integration.md`） |
| 4 | 環境変数の追加・変更 | `.env.example` 同期、秘密情報はハードコード禁止 |
| 5 | LP / ブランド表現の変更 | 禁止表現チェック、カラー定義フリーズ（`branding-identity.md`） |
| 6 | 300行超のファイルに追記するか？ | 分割を検討（`file-size-guard.md`） |
| 7 | UI / CSS を変更するか？ | スクリーンショットで確認、同一箇所3回修正で中断 |
| 8 | 広範囲の変更か？ | `git diff main --stat` で先祖返りチェック |

# ── 仕様設計パート ──

## フェーズ 1: 自律調査

ユーザーの要望を受けたら、質問する前にまず以下を調査する。

1. **アーキテクチャマップを読む**: `docs/architecture.md` — 機能がどのレイヤーに属するかを特定
2. **TODOを確認**: `todo.md` — 該当タスクの Phase・進捗状況を把握
3. **既存仕様を全件リスト化**: `spec/` の仕様ファイルを一覧し、関連仕様を読む
4. **整合性チェックリストを作る**: 既存仕様、既存コード、データモデルとの接点と矛盾を洗い出す
5. **テンプレートを読む**: `spec/_template.md`
6. **教訓チェック**: フェーズ 0 の該当項目を特定し、仕様書に反映する節を計画する

## フェーズ 2: 設計方針提案

設計方針は自分で決めて提案する。判断を求める時は、案ごとのメリット・デメリットを必ず書く。

```markdown
## 設計方針

### 案A
- やること:
- メリット:
- デメリット:

### 案B
- やること:
- メリット:
- デメリット:

→ 推奨案: 案A
```

## フェーズ 3: 仕様書作成

- `spec/feature-{name}.md` を作成または更新する
- Acceptance Criteria はテスト可能な粒度にする
- Cross-Reference を残す
- Out of Scope を明記する
- 曖昧な表現は避ける
- 既存仕様と矛盾する場合は修正案もセットで示す
- **フェーズ 0 で該当した項目は専用セクションとして仕様書に含める**（例: `## マルチテナント設計`, `## 状態遷移`, `## 環境変数`）

## フェーズ 4: レビュー用サマリー → ユーザー承認ゲート

以下をユーザーに提示し、**承認を得てから実装に進む**:

- 目的
- 主要要件
- 既存実装への影響
- トレードオフ
- Out of Scope

**⚠️ ユーザーの承認なしに実装フェーズに進まないこと。**

# ── 実装パート ──

## フェーズ 5: 実装事前調査

1. **仕様書を熟読**: `spec/feature-*.md` の Acceptance Criteria を把握
2. **アーキテクチャを確認**: `docs/architecture.md` で変更レイヤーと依存方向を確認
3. **既存実装を調査**: 対象ファイルを Read / Grep で確認し、影響範囲を把握
4. **実装計画を宣言**: どのファイルに何を変更するかを短く共有
5. **教訓チェック**: フェーズ 0 の該当項目を特定し、実装計画に制約として明記する

## フェーズ 6: テスト駆動開発

### Red
- Acceptance Criteria をテストケースに変換する
- テストが失敗することを確認する

### Green
- 最小限の実装でテストを通す
- 依存方向、ログ規約、例外処理規約、既存パターンを守る

### Refactor
- 可読性、重複、責務分離を改善する

## フェーズ 7: 検証

以下を基本として、存在するコマンドを実行する。

```bash
pnpm test
pnpm check
pnpm build
```

- コマンドが存在しない場合は、等価コマンドで代替する
- テスト、型チェック、ビルドのうち何を実行したかを完了報告に含める

## フェーズ 8: TODO更新と完了報告

### TODO更新
検証がパスしたら、`todo.md` を確認し:
- 実装した機能に対応する `[ ]` 項目を `[x]` に更新
- 該当項目がなければ、適切なセクションに完了項目として追記

### 完了報告
- 変更ファイル一覧と差分サマリー
- テスト結果
- Acceptance Criteria の充足状況
- 実行した検証コマンド
