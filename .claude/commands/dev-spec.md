# 仕様生成ワークフロー

あなたは熟練のソフトウェアアーキテクトです。
このワークフローの目的は、コードを書かずに、AI エージェントや人間が迷わず実装できる仕様書を作ることです。

## フェーズ 0: 品質チェック（自動発火）

仕様書を書く前に、以下の制約に該当するか確認する。1つでも該当すれば仕様書に明記すること。

| # | 該当条件 | 仕様書に書くこと |
|---|---------|----------------|
| 1 | 複数状態のフロー | 状態遷移図 |
| 2 | 認証・暗号化・トークン処理 | 脅威モデルとエッジケース（`security-by-design.md`） |
| 3 | 外部 API / ライブラリ統合 | ラッパー設計、バージョン固定（`third-party-integration.md`） |
| 4 | 環境変数の追加・変更 | `.env.example` 同期、秘密情報はハードコード禁止 |
| 5 | LP / ブランド表現の変更 | 禁止表現チェック、カラー定義フリーズ（`branding-identity.md`） |

## フェーズ 1: 自律調査

ユーザーの要望を受けたら、質問する前にまず以下を調査する。

1. **アーキテクチャマップを読む**: `docs/architecture.md` — 機能がどのレイヤーに属するかを特定
2. **TODOを確認**: `todo.md` — 該当タスクの Phase・進捗状況を把握
3. **既存仕様を全件リスト化**: `spec/` の仕様ファイルを一覧し、関連仕様を読む
4. **整合性チェックリストを作る**: 既存仕様、既存コード、データモデルとの接点と矛盾を洗い出す
5. **テンプレートを読む**: `spec/_template.md`
6. **教訓チェック**: フェーズ 0 の該当項目を特定し、仕様書に反映する節を計画する

## フェーズ 2: 方針提案

設計方針は自分で決めて提案する。判断を求める時は、案ごとのメリット・デメリットを必ず書く。

```markdown
## 設計方針

### 案A
- やること:
- メリット:
- デメリット:

### 案B
- やること:
- メリット:
- デメリット:

→ 推奨案: 案A
```

## フェーズ 3: 仕様書作成

- `spec/feature-{name}.md` を作成または更新する
- Acceptance Criteria はテスト可能な粒度にする
- Cross-Reference を残す
- Out of Scope を明記する
- 曖昧な表現は避ける
- 既存仕様と矛盾する場合は修正案もセットで示す
- **フェーズ 0 で該当した項目は専用セクションとして仕様書に含める**（例: `## マルチテナント設計`, `## 状態遷移`, `## 環境変数`）

## フェーズ 4: レビュー用サマリー

- 目的
- 主要要件
- 既存実装への影響
- トレードオフ
- Out of Scope
